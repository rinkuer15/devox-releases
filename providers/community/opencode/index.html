OpenCode (Community Provider)

note OpenCode is a community provider — contributed and maintained by the community (@opencode-ai/sdk). It is registered as builtIn: false.

Connect Devox to OpenCode for a multi-provider AI coding agent with support for Anthropic, OpenAI, Google, and more through a unified SDK. OpenCode provides file-based agent configuration, MCP server support, and a native plugin hook system.

Provider ID: opencode · Built-in: ❌ (community) · SDK: @opencode-ai/sdk

Prerequisites

Section titled “Prerequisites”
  • Devox installed (see Getting Started)
  • The opencode CLI installed separately and on your PATH (see below)
  • Credentials for your chosen LLM backend (Anthropic, OpenAI, Google, etc.)

Install

Section titled “Install”

Devox bundles the @opencode-ai/sdk npm package as a dependency of @devox/providers — that part needs no separate install and is available immediately after bun install. However, the SDK is only a thin client: at runtime it spawns the opencode CLI binary itself via opencode serve (using cross-spawn against your PATH). The CLI binary is not bundled with Devox and must be installed separately, the same as the Claude Code or Codex CLIs.

macOS / Linux / WSL:

Alternatives:

MethodCommand
npm (any platform)npm install -g opencode-ai
Homebrewbrew install sst/tap/opencode

Verify the install with opencode --version, then confirm it resolves on PATH: which opencode (macOS/Linux) or where opencode (Windows). If Devox reports OpenCode failed to create a session or similar startup errors, check this first — it is almost always a missing/unreachable opencode binary or a version mismatch with the bundled @opencode-ai/sdk.

How Devox Runs OpenCode

Section titled “How Devox Runs OpenCode”

Devox always runs OpenCode as a managed embedded runtime — it spawns and owns the OpenCode server process, generates a random server password per session, and tears it down when the workflow completes. Connecting to an external OpenCode server is not supported.

Agents

Section titled “Agents”

OpenCode uses file-based agent configuration via .opencode/opencode.json. You can also define inline agents in workflow YAML — Devox materializes them to temporary files before execution:

note[Agents semantics] OpenCode agents differ from Claude SDK agents: OpenCode uses config-file-based agent selection rather than programmatic inline agent definitions. Devox’s agents: YAML translation materializes agents to config files — this is not the same as Claude SDK’s options.agents array.

Hooks

Section titled “Hooks”

OpenCode has its own native plugin hook system configured via .opencode/opencode.json. This system works fully and independently of Devox:

note[Devox workflow hooks: field] Devox’s workflow hooks: YAML field is passed as node config but not forwarded to the OpenCode runtime — inline hook definitions in workflow YAML are silently ignored. Use OpenCode’s native .opencode/opencode.json hooks instead. Additionally, hooks: defined in agent file definitions are dropped with a logged warning — the OpenCode agent file format does not support the Devox hook schema.

Capabilities

Section titled “Capabilities”
CapabilitySupportedNotes
Session resume✅Single-agent runs return sessionId; multi-agent runs do not
MCP servers✅mcp: path/to/servers.json passed through to OpenCode
Hooks✅OpenCode’s native plugin system via .opencode/opencode.json
Skills✅SKILL.md files resolved from .agents/skills/ and .claude/skills/
Inline sub-agents✅File-materialized agents; single and parallel multi-agent fan-out
Tool restrictions✅tools / disallowedTools per agent; deny wins over allow
Structured output✅output_format: — schema passed to OpenCode SDK
Env injection✅Merged into the spawned OpenCode environment
Cost control (maxBudgetUsd)❌Cost tracked in result chunks, no runtime enforcement
Effort control❌Not configurable per-request; set in OpenCode config
Thinking control❌Auto-enabled when using a reasoning-capable model
Fallback model❌No native failover in the SDK
Sandbox❌Devox uses worktree isolation instead
Native in-process tools✅—

Unsupported YAML fields trigger a visible warning from the dag-executor. Your workflow still executes — the field is ignored.
