Bundled Hooks

Bundled hooks are shell scripts shipped inside the Devox binary. Run devox hooks install once and they are extracted to disk and registered with your AI providers. Every Claude and Copilot session automatically runs them — no workflow changes required.

Claude and Copilot support native hooks. Codex and Pi have no hook API; scripts are extracted for manual use.

Hook Discovery Hierarchy

Section titled “Hook Discovery Hierarchy”

Hooks use a 3-layer merge — later layers override earlier ones by name:

LayerLocationUse Case
BundledInside Devox binaryDefaults shipped with every install
Global~/.devox/hooks/Your personal overrides, apply everywhere
Project<cwd>/.devox/hooks/Project-specific hooks and overrides

A pre-commit-quality-gate.sh in ~/.devox/hooks/ replaces the bundled version. A same-named file in .devox/hooks/ replaces both.

The 8 Bundled Hooks

Section titled “The 8 Bundled Hooks”

pre-commit-quality-gate

Section titled “pre-commit-quality-gate”
  • Event: PreToolUse
  • Matcher: Bash (git commit)
  • What it does: Scans the staged diff for console.log, debugger, and hardcoded secrets (API keys, passwords, tokens). Exits 2 on critical findings (blocks the commit). Emits warnings on minor issues.
  • Codex/Pi fallback: Built into the commit command with equivalent checks.

post-edit-typecheck

Section titled “post-edit-typecheck”
  • Event: PostToolUse
  • Matcher: Edit (.ts, .tsx files)
  • What it does: Runs tsc --noEmit immediately after TypeScript edits. Surfaces type errors in-context so the AI can fix them before moving on.

post-edit-lint

Section titled “post-edit-lint”
  • Event: PostToolUse
  • Matcher: Edit (.ts, .js, .py, .rs files)
  • What it does: Runs ESLint (TypeScript/JavaScript), Ruff (Python), or Clippy (Rust) on the edited file. Respects each project’s own linter config.

dev-server-blocker

Section titled “dev-server-blocker”
  • Event: PreToolUse
  • Matcher: Bash
  • What it does: Detects bun dev, npm run dev, pnpm dev, yarn dev without & or tmux. Blocks the command and suggests bun dev & to prevent the AI from hanging on a blocking process.

pr-url-logger

Section titled “pr-url-logger”
  • Event: PostToolUse
  • Matcher: Bash (gh pr create)
  • What it does: Extracts the PR URL from gh pr create output and appends it to .devox/state/prs.log. Keeps a searchable history of all PRs created in the project.

session-summary

Section titled “session-summary”
  • Event: Stop (Claude) / SessionEnd (Copilot)
  • What it does: Persists a JSONL session summary to .devox/state/session-history.jsonl. Useful for retrospectives and for context when resuming work.

instinct-extractor

Section titled “instinct-extractor”
  • Event: Stop (Claude) / SessionEnd (Copilot)
  • What it does: Evaluates the session for extractable patterns and appends them to .devox/state/instincts.json. Over time this file accumulates project-specific insights that can be promoted to rules.

context-compact-reminder

Section titled “context-compact-reminder”
  • Event: PreToolUse
  • Matcher: Edit|Write
  • What it does: Counts tool calls. Around 50 calls, injects a suggestion to run /compact to avoid context window overflow.

Opt-In Hooks

Section titled “Opt-In Hooks”

These hooks are disabled by default. Enable them explicitly via the include list in config.

config-protection

Section titled “config-protection”
  • Event: PreToolUse
  • Matcher: Edit|Write
  • What it does: Blocks modifications to linter/formatter config files (ESLint, Prettier, Biome, Ruff, etc.). AI agents frequently weaken rules instead of fixing code. This hook forces the agent to fix source code, not weaken the config.
  • Allows: First-time creation (no existing config to weaken).
  • Status: Disabled by default — enable via include: ['config-protection'] in config.
  • When to enable:
    • Teams that want to enforce quality standards
    • Projects with established linter rules that should not be weakened
    • When you’ve caught the AI editing .eslintrc to make errors pass
  • When NOT to enable:
    • Solo projects where you want flexibility to adjust rules
    • During initial project setup when config files are being iteratively refined

block-no-verify

Section titled “block-no-verify”
  • Event: PreToolUse
  • Matcher: Bash
  • What it does: Blocks git commit --no-verify, git push --no-verify, and -c core.hooksPath= bypass attempts. Protects pre-commit, commit-msg, and pre-push hooks from being skipped.
  • Status: Disabled by default — enable via include: ['block-no-verify'] in config.
  • When to enable:
    • Projects with mandatory pre-commit checks (security scanning, test running)
    • Teams that rely on git hooks for quality gates
    • Enterprise environments with compliance requirements
  • When NOT to enable:
    • Workflows that legitimately need emergency hotfix commits
    • Projects that intentionally bypass hooks for WIP commits

post-session-token-cost (CodeBurn integration)

Section titled “post-session-token-cost (CodeBurn integration)”
  • Event: Stop (Claude) / SessionEnd (Copilot)
  • What it does: After every AI session ends, runs bunx codeburn status --format json and appends a cost snapshot to ~/.devox/state/token-cost.jsonl. Powers the devox-token-report and devox-cost-audit workflows.
  • Requires: bunx on PATH (comes with Bun). CodeBurn is downloaded on first use.
  • Status: Disabled by default — enable via include.
  • Output: One JSON line per session: {"timestamp":"...","today_cost":4.07,"month_cost":339.47,"branch":"main"}

budget-alert (CodeBurn integration)

Section titled “budget-alert (CodeBurn integration)”
  • Event: UserPromptSubmitted
  • What it does: Before every prompt, checks today’s spend. If it exceeds DEVOX_DAILY_BUDGET (default $5), injects a warning into the AI context so it knows to be conservative with tool calls.
  • Requires: bunx on PATH. Silently skips if CodeBurn is unavailable.
  • Status: Disabled by default — enable via include.
  • Configure budget: DEVOX_DAILY_BUDGET=10 bun run dev (or export in shell profile).

CLI Reference

Section titled “CLI Reference”

devox hooks list

Section titled “devox hooks list”

Show active hooks grouped by trigger event, with install status.

--global and --local are mutually exclusive. The default (no scope flag) merges all three layers — project overrides global by name, global overrides bundled.

If hooks have never been installed, the output shows a warning and a reminder to run devox hooks install.

devox hooks install

Section titled “devox hooks install”

Extract bundled hook scripts to disk and register them with your AI providers.

What happens step by step:

  1. Hook scripts (.sh files) are extracted from the embedded binary to disk
  2. Unless --no-claude: .claude/settings.json (or ~/.claude/settings.json for --global) is patched with hook registrations
  3. Unless --no-copilot: assistants.copilot.hooks is written into .devox/config.yaml (or ~/.devox/config.yaml for --global)

--force explained: By default, hooks install skips any .sh file that already exists on disk. This preserves edits you may have made to a bundled hook. Use --force to reset scripts back to the bundled defaults — useful after a Devox upgrade that ships improved hooks, or when a script has been accidentally corrupted.

--no-claude / --no-copilot: Use these when you want the scripts on disk (for manual use or custom wiring) without Devox auto-registering them in provider configs.

Re-running devox hooks install without --force is safe — existing scripts are skipped and existing provider config entries are preserved.

Binary vs source: In the shipped Devox binary, hook scripts are embedded at compile time. hooks install extracts them from that embedded bundle. In source builds (bun run cli), scripts are read from .devox/hooks/defaults/ on the filesystem. The result on disk is identical either way.

devox hooks disable / enable

Section titled “devox hooks disable / enable”

disable adds the hook name to globalHooks.exclude in the appropriate config.yaml. enable removes it. The script file stays on disk — only the config entry changes. This means you can re-enable a hook at any time without re-running hooks install.

Complete Priority Chain

Section titled “Complete Priority Chain”

Within each config file, the hook filter applies in this order:

  1. loadDefaultHooks: false → disables ALL hooks (overrides everything else)
  2. Opt-in hooks (enabledByDefault: false) → filtered out unless in include
  3. include list → exclusive allowlist (if set, only listed hooks run)
  4. exclude list → denylist (removed after include filtering)

Codex / Pi

Section titled “Codex / Pi”

No native hook API. Scripts are extracted to ~/.devox/hooks/ for manual use:

  • Use the commit command (has quality gate logic built in) instead of raw git commit
  • Add bash: nodes in workflows that call the scripts explicitly
  • Reference scripts from custom bash: pre-steps in your workflows

Troubleshooting

Section titled “Troubleshooting”

Hooks not running after install
Verify .claude/settings.json has the hook entries. Run devox hooks list to confirm hooks are discovered. Re-run devox hooks install --global.

Pre-commit gate blocking valid commits
The gate is conservative. If it’s triggering false positives, override pre-commit-quality-gate.sh at ~/.devox/hooks/pre-commit-quality-gate.sh with your own version, or disable it:

Copilot hooks not firing
Verify assistants.copilot.hooks is present in your ~/.devox/config.yaml (or <cwd>/.devox/config.yaml). Run devox hooks install --global to write it. Copilot hook support requires the gh copilot extension version that supports the hooks: config key.

devox doctor shows hooks not installed
Run devox hooks install --global. The doctor check looks for .sh files in ~/.devox/hooks/.
