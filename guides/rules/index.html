Global Rules

Global Rules are Markdown documents that Devox automatically injects into the system prompt of every AI call — direct chat, workflow nodes, and sub-agents alike. Unlike skills (opt-in per node) or hooks (event-driven), rules are always-on constraints that every provider sees identically.

Works with all providers — Claude, Copilot, Codex, Pi, and any future provider. Rules are injected at the prompt level before the provider SDK is called, so no provider-specific configuration is needed.

The Three Layers

Section titled “The Three Layers”

Rules load and merge from three locations. Higher layers override lower layers when two files share the same name (filename without .md).

LayerPathPriority
BundledEmbedded in the Devox binaryLowest
User-global~/.devox/rules/Middle
Project.devox/rules/ (in your repo)Highest

Devox ships with three bundled rules enabled by default. You can disable them, override them, or add your own.

Bundled Rules

Section titled “Bundled Rules”

Three rules are bundled with Devox and active by default:

always

Section titled “always”

Hard constraints that apply universally:

  • Never hardcode secrets, API keys, or credentials — use env vars or secret managers
  • Never leave console.log, debugger, or TODO: remove in committed code
  • All functions and exported symbols must have TypeScript types (no implicit any)
  • All errors must be caught and either handled explicitly or re-thrown — no silent swallows
  • Prefer immutable data (never mutate function arguments or shared state)
  • Before committing: confirm no secret leakage, no debug artefacts, no broken imports

code-quality

Section titled “code-quality”

Code quality standards derived from KISS/DRY/YAGNI:

  • Single file ≤ 400 lines (warn), hard limit 800 lines — split if exceeded
  • Functions ≤ 50 lines — extract helpers if longer
  • Avoid clever one-liners when a readable multi-line version exists
  • Extract shared logic only after the same pattern appears 3+ times
  • Each module has one responsibility — no god files mixing transport, logic, and storage
  • Only comment non-obvious decisions; never add comments that restate the code

security

Section titled “security”

An 8-item security checklist enforced on every change:

  1. No secrets, API keys, tokens in source code or logs
  2. All external inputs validated and sanitised before use
  3. SQL/NoSQL queries use parameterised statements — no string interpolation
  4. Auth checks happen at the entry point, not deep in business logic
  5. HTTP responses never expose stack traces or internal paths to clients
  6. CSRF tokens present on all state-mutating endpoints (POST/PUT/PATCH/DELETE)
  7. Rate limiting applied to all public-facing endpoints
  8. npm audit / bun audit run and passing — no high-severity CVEs in dependencies

Naming

Section titled “Naming”
  • File name becomes the rule name (without .md)
  • Names are case-sensitive — security.md and Security.md are different rules
  • Use lowercase kebab-case: api-conventions.md, team-style.md

Section titled “Rules vs Standards vs Other Features”

Rules and Standards are complementary, not competing:

Rules.devox/rules/Every AI call, alwaysCompact checklists — ≤ 20 bullets per fileAll providers
Standards.devox/standards/On demand — loaded by prime-* commandsDetailed reference docs with code examplesClaude (reads files)

Which topics live where

Section titled “Which topics live where”
TopicRulesStandards
Secrets / no debug / immutabilityalways.md ✅—
KISS / DRY / YAGNI / file size / namingcode-quality.md ✅—
Security checklist + OWASPsecurity.md ✅—
Testing — TDD / AAA / coverage / mocks—testing.md ✅
Git — branch naming / conventional commits / PR—git-workflow.md ✅
Agent usage / delegation / prompt defense—agents.md ✅
TypeScript — strict / Zod / imports / error types—typescript.md ✅
Python — type hints / dataclasses / async—python.md ✅
Performance — profile first / benchmark / DB—performance.md ✅

Rule of thumb: if a constraint should fire on every single AI call and can be expressed in 1-2 sentences, put it in a rule. If it needs code examples, tables, or detailed rationale, it belongs in a standard.

Use rules for non-negotiable constraints that should never be absent. Use skills for deep domain knowledge that only specific nodes need. Use systemPrompt: for workflow-specific framing.

Tips

Section titled “Tips”

Keep rules short and actionable. Rules appear in every prompt. Long, vague rules waste context budget and get ignored. Prefer:

One concern per file. A security.md for security rules, style.md for style rules. This makes it easy to override just one area without touching others.

Test your rules. Ask the AI: “What rules are currently active?” — it will recite the ## Active Rules section injected into its context. If a rule is missing, check the file path and .devox/config.yaml.

Project rules win. If a team standard conflicts with your personal global rule, add a .devox/rules/<name>.md in the repo — it will override your ~/.devox/rules/<name>.md automatically.
