Node Artifacts & Cross-Run Output

Devox has two separate mechanisms for sharing a node’s output with other nodes. Knowing which one to use depends on when the consumer runs.

MechanismConsumer runs…Storage
$nodeId.outputSame run, downstream nodeIn-memory
output_type + $PREV_<TYPE>Any later run, any workflowDisk (~/.devox/…/artifacts/)

Same-run: $nodeId.output

Section titled “Same-run: $nodeId.output”

The simplest form — pass output forward inside one workflow run. No extra configuration needed.

The depends_on field ensures plan runs first. $plan.output is substituted with the full text output of the plan node.

Cross-run: output_type + $PREV_<TYPE>

Section titled “Cross-run: output_type + $PREV_<TYPE>”

When you want a future run (or a completely different workflow) to pick up where a past run left off, use output_type.

How it works

Section titled “How it works”

  1. Producer node — declare output_type: <label> on any node. When the node completes, Devox writes two files to the run’s artifacts directory:

  2. Consumer node — reference it in any future prompt with $PREV_<TYPE> (UPPER_SNAKE of the output_type label).

    The executor scans all past runs for the project and inlines the most recently produced artifact of that type.

caution[Naming collision in bash: / script: nodes] $PREV_<TYPE> substitution is a blanket regex over the entire node text — it matches any $PREV_word token, not just an intentional placeholder. If a bash: or script: node’s own logic declares a local variable whose name also starts with PREV_ (e.g. PREV_CONTENT, PREV_RESULT), that variable reference gets silently replaced too — usually with an empty string, since no artifact of that made-up “type” exists.

Rule of thumb: never name a local shell/script variable starting with PREV_ in a node that also uses $PREV_<TYPE> substitution.

Example — multi-run iterative workflow

Section titled “Example — multi-run iterative workflow”

First run: $PREV_FINDINGS is empty — research starts from scratch. Second run: $PREV_FINDINGS contains the first run’s output — research extends it. Each run accumulates knowledge from all prior runs.

Cross-workflow sharing

Section titled “Cross-workflow sharing”

$PREV_<TYPE> looks across all workflows on the same project — not just the same workflow file. Any workflow can consume an artifact produced by any other workflow, as long as they share the same project root.

Cold-resume recovery pointer (persist_session nodes)

Section titled “Cold-resume recovery pointer (persist_session nodes)”

A node with persist_session: true (or a workflow with persist_sessions: true, see Authoring Workflows) asks the provider to resume its own prior AI session the next time the same workflow runs in the same conversation — not just re-read artifacts, but continue the actual conversation with full in-context memory.

Sometimes the provider can’t honor that: the session may have expired, been evicted, or belong to a provider version that no longer recognizes the id. When this happens the provider silently starts a fresh session instead of resuming — a “cold resume.” Without any signal, this looks identical to a normal successful run, except the node has quietly lost all context from its previous conversation.

Devox detects this and tells you about it:

  1. Every node that participates in session persistence also mirrors its typed output_type artifact into a stable, cross-invocation scope directory (artifacts/scopes/<workflow-name>/<conversation-id>/), separate from the per-run artifacts/runs/<run-id>/ directory. This mirror is best-effort and only happens for nodes that use persist_session.

  2. When a node requested a session resume and the provider reports it did not actually resume, Devox sends a warning message:

    ⚠️ Node planner expected to resume a persisted session but the provider started a fresh one instead (cold resume). Continuing without prior conversation context.

  3. If the scope directory has artifacts from a prior invocation, the warning is followed by a recovery pointer — a by-reference list of file paths (never pasted content) so you (or a downstream node instructed to read them) can recover the lost context on demand:

The node is not failed or re-run — cold resume is a silent-context-loss warning, not an error. The workflow continues normally with the fresh session. This is purely additive: workflows that don’t use persist_session never create a scope directory and never see this warning.

Setting output_type in the Web UI

Section titled “Setting output_type in the Web UI”

In the Workflow Builder, select any non-approval node and look for the Output Type field in the General tab of the node inspector.

  • Type a lowercase label (e.g. plan, report, findings)
  • The field auto-formats to kebab-case
  • The hint text shows the corresponding $PREV_<TYPE> variable name to use in consumer nodes

Naming convention

Section titled “Naming convention”
output_type value$PREV_ variable
plan$PREV_PLAN
report$PREV_REPORT
test-results$PREV_TEST_RESULTS
code-review$PREV_CODE_REVIEW

Rules:

  • output_type is lowercase kebab-case in YAML (plan, test-results)
  • The $PREV_ variable is UPPER_SNAKE ($PREV_PLAN, $PREV_TEST_RESULTS)
  • Hyphens in the type become underscores in the variable name

Which node types support output_type?

Section titled “Which node types support output_type?”

All non-approval node types support it: prompt, command, bash, script, loop. Approval nodes do not run AI, so they do not produce typed artifacts.
