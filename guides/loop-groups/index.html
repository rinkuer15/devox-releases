Loop Groups

DAG workflow nodes support a loop_group field that repeats a multi-node sub-DAG each iteration, using the exact same completion-gate semantics as Loop Nodes (until, until_field, until_bash, max_iterations, fresh_context, interactive/gate_message).

Use a loop group when a single AI prompt isn’t enough per iteration — for example, running a deterministic bash check, then an AI fix, then a script validation, all as one repeating unit.

Quick Start

Section titled “Quick Start”

loop: vs loop_group:

Section titled “loop: vs loop_group:”
loop:loop_group:
RepeatsOne AI prompt or commandA full sub-DAG of nodes
Body node typesN/A (single prompt)bash, script, command, prompt, nested loop, nested loop_group
provider / modelIgnored (workflow default always used)Forwarded as defaults to body AI nodes (each still overridable per body node)
retryRejected at parse timeRejected at parse time
OutputLast iteration’s AI outputLast iteration’s terminal body node output

If a single prompt is enough, prefer loop: — it’s simpler. Reach for loop_group: when the repeating unit is genuinely a small pipeline.

Configuration Fields

Section titled “Configuration Fields”

These iteration-control fields behave identically to Loop Nodes — see that guide for the full semantics of until (tag vs plain signal matching), until_field (structured-JSON completion field), max_iterations (hard fail on exceed), fresh_context (session continuity), until_bash (deterministic exit check), and interactive/gate_message (human-in-the-loop pausing). This guide covers only what’s specific to the multi-node body.

nodes (the repeating body)

Section titled “nodes (the repeating body)”

An array of full DAG nodes, wired together with depends_on exactly like a top-level workflow:

  • Nodes without depends_on run first; nodes in the same topological layer run concurrently.
  • Body node ids only need to be unique within the group — they’re private to the group and are re-namespaced against the group’s own id at execution time.
  • $bodyNodeId.output refs work between body nodes, the same as top-level $nodeId.output refs.
  • Body nodes can reference outer-scope node outputs too (e.g. $setup.output from a node outside the group) — the outer scope’s already-completed outputs are visible inside every iteration.

Supported body node kinds: bash, script, command, prompt, nested loop, and nested loop_group.

Not supported inside a loop_group body: approval, workflow, and include. These are rejected at parse time. Reasoning:

  • approval — every iteration would need to compose two independent pause/resume state machines (the group’s own gate and the approval gate), which the resume/cancel state tracking doesn’t model.
  • workflow (sub-workflow invocation) — sub-workflow session/DB-write semantics assume a single top-level execution, not per-iteration re-invocation.
  • include — this is a load-time-only directive that must already be expanded away by the include-expander before the schema even sees a loop_group body; a literal include: surviving to this point is a loader bug, not a valid body node.

If you need a human checkpoint inside an iterative process, put the loop_group behind (or in front of) a top-level approval node instead of nesting the approval inside the group.

provider / model forwarding

Section titled “provider / model forwarding”

Unlike plain loop: (which always uses the workflow-level provider/model and ignores any override), loop_group does forward its own provider/model as defaults to AI body nodes — each body node can still set its own provider/model to override that default:

Every other AI-only field set directly on the loop_group node itself (output_format, allowed_tools, hooks, mcp, skills, agents, effort, thinking, etc.) is parsed but ignored with a loader warning — those fields belong on individual body nodes, not the group.

Output

Section titled “Output”

The group node’s output ($myLoopGroup.output, available to downstream nodes) is the last iteration’s terminal body node output — i.e. the output of whichever body node no other body node depends on (mirroring how the top-level executor picks a workflow’s terminal-node output). If you need outputs from every iteration, write them to $ARTIFACTS_DIR from within the body.

Resume and cancel

Section titled “Resume and cancel”

A loop_group participates in the same resume/cancel state tracking as every other node type:

  • Cancel — checked between iterations (same as loop:); an in-progress iteration’s body nodes are not force-killed mid-layer, but no new iteration starts once cancellation is detected.
  • Resume (/workflow resume <id>) — an interactive loop group paused at a gate resumes from the next iteration, with $LOOP_USER_INPUT populated from the approval feedback on that first resumed iteration only (empty on subsequent iterations), identical to loop:.
  • retry: is rejected at parse time on loop_group nodes — the group manages its own iteration semantics internally; individual body nodes may still declare their own retry: if needed.

Nested Loop Groups

Section titled “Nested Loop Groups”

Because a loop_group’s body is itself an array of full DAG nodes, nesting is supported for free:

Use nesting sparingly — it’s easy to construct a combinatorially large number of iterations (outer.max_iterations × inner.max_iterations).

Interaction with include:

Section titled “Interaction with include:”

If a loop_group node lives inside a workflow that gets pulled in via include:, the include-expander correctly rewrites $id.output refs found inside the group’s body prompts that point to sibling nodes outside the group (renaming them to the included workflow’s namespaced ids), while leaving refs to other body nodes in the same group untouched (those are private to the group and never collide with the included workflow’s top-level ids).
