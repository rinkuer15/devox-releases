Web Authentication

Devox ships with authentication disabled by default. On a personal machine you can reach the Web UI without logging in and everything works. This is the right default for a solo developer.

When you expose Devox to teammates or the internet you want to gate access: only registered users should be able to trigger workflows that run against your API keys.

Three env vars unlock the full stack:

Env varPurpose
DATABASE_URLMust be PostgreSQL — auth tables are Postgres-only
BETTER_AUTH_SECRET32+ character secret used to sign session tokens
TOKEN_ENCRYPTION_KEY64-char hex key used to encrypt stored API keys and GitHub tokens

Feature 1 — Login screen (Better Auth)

Section titled “Feature 1 — Login screen (Better Auth)”

What it does

Section titled “What it does”

When DATABASE_URL (PostgreSQL) and BETTER_AUTH_SECRET are both set, isWebAuthEnabled() returns true and:

  • The Web UI redirects unauthenticated visitors to /login
  • Email + password sign-up / sign-in is available
  • A SessionGate component wraps the entire app — no content is served without a valid session
  • Every /api/* route that requires a user identity returns 401 for unauthenticated requests

Without those two env vars the login page is never shown and all existing behaviour is unchanged.

Signup modes

Section titled “Signup modes”

The DEVOX_AUTH_OPEN_SIGNUP and DEVOX_AUTH_ALLOWED_EMAILS env vars control who can register:

ConfigurationModeBehaviour
Neither setdisabledSignup is off — login only. Useful once the admin account is created.
DEVOX_AUTH_OPEN_SIGNUP=trueopenAnyone who can reach the URL may register.
DEVOX_AUTH_ALLOWED_EMAILS=a@b.com,...allowlistOnly listed emails may sign up. Others get a 403.

Set DEVOX_AUTH_OPEN_SIGNUP=false (or remove the var) after creating your initial account to close registration.

API gate

Section titled “API gate”

By default, every /api/* call is checked against the session. Set DEVOX_WEB_AUTH_REQUIRED=false to keep the login UI but skip server-side API enforcement (useful when a reverse proxy already gates access).

Feature 2 — Per-user AI provider keys

Section titled “Feature 2 — Per-user AI provider keys”

What it does

Section titled “What it does”

By default, all users share the server’s API keys from .env (ANTHROPIC_API_KEY, OPENAI_API_KEY, etc.) and all AI usage is billed to the same account.

With TOKEN_ENCRYPTION_KEY set, each logged-in user can connect their own API key per provider. When a workflow or chat session runs:

  • The logged-in user’s stored key is decrypted at runtime
  • It is injected as an env var override (wins over the server’s .env)
  • User A’s Anthropic key is used for User A’s sessions; User B’s key for User B’s

Keys are encrypted with AES-256-GCM before being written to the database and are never returned in any API response.

Connecting a key in the Web UI

Section titled “Connecting a key in the Web UI”
  1. Log in and go to Settings
  2. Scroll to the bottom — the “AI Provider Keys” card appears (only when auth is enabled)
  3. Click + next to a provider (e.g. anthropic, openai, google)
  4. Paste your API key and click Save
  5. The key is stored encrypted immediately — the plaintext is never shown again

Feature 3 — Per-user GitHub identity (device flow)

Section titled “Feature 3 — Per-user GitHub identity (device flow)”

What it does

Section titled “What it does”

By default, Devox uses a single shared GH_TOKEN (PAT) for all GitHub operations — PRs, commits, and pushes are attributed to whoever owns that token.

With a GitHub App configured, each user can connect their own GitHub account via the OAuth Device Flow:

  • PRs and commits are opened under the user’s own GitHub identity
  • Workflows declaring requires: [github] block unconnected users with a clear message
  • Tokens auto-refresh before expiry — no re-authentication needed

GitHub tokens are also encrypted at rest with TOKEN_ENCRYPTION_KEY.

Prerequisites

Section titled “Prerequisites”

This feature requires:

  1. TOKEN_ENCRYPTION_KEY (see Feature 2 above)
  2. A GitHub App with Device Flow enabled (one-time setup, ~5 minutes)

note[Solo install — skip this] If you’re the only user, your existing GH_TOKEN PAT already handles all GitHub operations. You only need per-user GitHub if you share Devox with teammates and want commits attributed to each person.

Creating a GitHub App

Section titled “Creating a GitHub App”
  1. Go to github.com/settings/apps/new
  2. Fill in:
    • App name: anything (e.g. Devox-MyOrg)
    • Homepage URL: your Devox URL (e.g. http://localhost:3090)
    • Webhook: uncheck “Active”
  3. Under Permissions, set at minimum:
    • Contents: Read & Write
    • Pull requests: Read & Write
  4. Click Create GitHub App
  5. On the App settings page:
    • Copy the App ID (numeric, top of page)
    • Copy the Client ID (starts with Iv1. or Iv23...)
  6. Under “Identifying and authorizing users”, tick ✅ “Enable Device Flow” and save

Connecting GitHub in the Web UI

Section titled “Connecting GitHub in the Web UI”
  1. Log in and go to Settings
  2. Scroll to the bottom — the “GitHub Account” card appears (only when GITHUB_APP_ID is configured)
  3. Click Connect GitHub
  4. A code like ABCD-1234 appears in the card
  5. Open github.com/login/device in your browser and enter the code
  6. Authorise the App
  7. The card updates to “Connected as @yourusername” automatically

You don’t type anything into Devox — the code entry happens entirely on GitHub’s website.

Schema auto-migration

Section titled “Schema auto-migration”

All auth tables (remote_agent_auth_user, remote_agent_auth_session, remote_agent_auth_account, remote_agent_auth_verification, remote_agent_user_provider_keys, remote_agent_user_github_tokens) are created automatically on first server start — no manual SQL required.

The same bootstrap runs during devox setup when you select PostgreSQL, so new installs are fully initialised before the wizard exits.
