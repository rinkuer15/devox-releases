Database

Devox supports two database backends: SQLite (default, zero setup) and PostgreSQL (optional, for cloud/advanced deployments). The database backend is selected automatically based on whether the DATABASE_URL environment variable is set.

SQLite (Default - No Setup Required)

Section titled “SQLite (Default - No Setup Required)”

Simply omit the DATABASE_URL variable from your .env file. The app will automatically:

  • Create a SQLite database at ~/.devox/devox.db
  • Initialize the schema on first run
  • Use this database for all operations

Pros:

  • Zero configuration required
  • No external database needed
  • Perfect for single-user CLI usage

Cons:

  • Not suitable for multi-container deployments
  • No network access (CLI and server can’t share database across different hosts)

Schema Overview

Section titled “Schema Overview”

The database has 28 tables (as of migration 041), all prefixed with remote_agent_ except Better Auth’s own auth_* tables (web login, opt-in). Grouped by domain:

DomainTables
Identitycodebases, codebase_env_vars, users, user_identities, user_github_tokens, user_provider_keys
Chat coreconversations, sessions, messages
Isolationisolation_environments
Workflowsworkflow_runs, workflow_events, workflow_node_sessions
Idea-to-Kanbanideas, idea_messages, tasks, guideline_documents
Knowledge/RAGknowledge_config, knowledge_sources
Notificationsnotifications
Web auth (Better Auth, opt-in)auth_user, auth_session, auth_account, auth_verification

Key tables in detail:

  1. remote_agent_codebases - Repository/workspace metadata

    • Commands stored as JSONB: {command_name: {path, description}}
    • AI assistant type, default working directory, allow_env_keys consent flag
    • kind — 'repo' (default, git-based, worktree-isolated) or 'folder' (plain local directory, git optional, always runs in place at default_cwd — no worktrees, no isolation environments) (migration 043)
    • orchestrator_conversation_id — the pinned, persistent orchestrator conversation for this codebase (migration 027, type-fixed in 038)
    • project_memory — free-form context injected into every orchestrator message (migration 028)

  2. remote_agent_conversations - Platform conversation tracking

    • Platform type + conversation ID (unique constraint)
    • Linked to codebase and (optionally) user_id and isolation_env_id
    • AI assistant type locked at creation; last_activity_at computed from latest message/session activity

  3. remote_agent_sessions - AI session management

    • Active session flag (one per conversation)
    • Session ID for resume capability; immutable — transitions create a new linked row (parent_session_id, transition_reason, ended_reason)

  4. remote_agent_isolation_environments - Worktree isolation

    • Tracks git worktrees per issue/PR/workflow run; enables worktree sharing between linked issues and PRs
    • updated_at and created_by_user_id added in migration 041 for parity with SQLite

  5. remote_agent_workflow_runs - Workflow execution tracking

    • Tracks active workflows per conversation
    • Locks concurrent execution per working_path: a second dispatch on a path with an active run (status pending/running/paused) is auto-cancelled with an actionable message. Stale pending rows older than 5 minutes are treated as orphaned and ignored.
    • Stores workflow state, step progress, and parent conversation linkage

  6. remote_agent_workflow_events - Step-level workflow event log

    • Records step transitions, artifacts, and errors per workflow run
    • input_tokens, output_tokens, model, cost_usd billing columns (migration 037)
    • Lean UI-relevant events (verbose logs stored in JSONL files)

  7. remote_agent_workflow_node_sessions (added in migration 030) - Per-node provider session persistence

    • Composite key (workflow_name, node_id, scope_key, provider) — no surrogate id
    • Lets a workflow node opt in to resuming its own AI session across re-runs via persist_session: true

  8. remote_agent_messages - Conversation message history

    • Persists user and assistant messages with timestamps and user_id (migration 039)
    • Stores tool call metadata (name, input, duration) in JSONB

  9. remote_agent_codebase_env_vars - Per-project env vars for workflow execution

    • Key-value pairs scoped to a codebase, injected into the AI SDK subprocess environment at execution time
    • Managed via Web UI Settings panel; env: in .devox/config.yaml for CLI users

  10. remote_agent_users / remote_agent_user_identities (added in migration 029) - Cross-platform user identity

    • users is the Devox-internal identity; user_identities maps (platform, platform_user_id) → user_id
    • user_github_tokens and user_provider_keys store encrypted per-user OAuth/API credentials

  11. remote_agent_ideas / remote_agent_idea_messages / remote_agent_tasks / remote_agent_guideline_documents (added in migration 022, extended in 023–026) - Idea-to-Kanban

    • Ideas support hierarchy (parent_idea_id), GitHub issue tracking, and kanban lifecycle statuses (backlog → todo → in_progress → done/blocked)
    • Tasks link back to an idea and optionally a workflow_run_id; carry priority and requirement_ref (migration 023)

  12. remote_agent_notifications (added in migration 040) - Durable notification inbox

    • Distinct from workflow_events (execution telemetry) — user-facing “you should look at this” records
    • Written when a workflow run completes/fails, an approval gate needs input, or a budget threshold is exceeded

  13. remote_agent_knowledge_config (added in migration 031, extended in 032–036) - Vector store configuration

    • Single-row table (primary key 'default') — one config per Devox install
    • Stores: vector_provider, vector_url, vector_api_key (encrypted at rest), embed_provider/embed_model, llm_provider/llm_model (migration 032), chunk size, similarity threshold, and crawl/code-extraction tuning parameters (migration 036)
    • Does not store vectors — only configuration metadata
    • Default: vector_provider = 'supabase', embed_provider = 'openai', hybrid search enabled

  14. remote_agent_knowledge_sources (added in migration 031, extended in 035) - Knowledge source tracking

    • One row per indexed source (URL, uploaded file, code folder)
    • Global — not scoped to any codebase. Any source can be used in any workflow from any project.
    • Tracks: name, type, location, status (pending → indexing → ready / error), knowledge_type (technical/business/general, migration 035), metadata (chunk count, word count, etc.)
    • Does not store vectors or text chunks — those live in the external vector store (Supabase / Qdrant / ChromaDB)

note[Vector data lives externally] Migration 031 only adds metadata tables to your Devox SQLite/PostgreSQL database. The actual text chunks and embedding vectors are stored in your configured external vector store (Supabase pgvector, Qdrant, or ChromaDB). See the Knowledge Base guide for vector store setup.

Entity Relationship Diagram

Section titled “Entity Relationship Diagram”

Generated from the full migration history (migrations/000_combined.sql, representing the combined state of migrations 001–041). The remote_agent_ table name prefix is omitted below for readability (e.g. codebases = remote_agent_codebases).

Notes on relationships not expressible as clean crow’s-foot lines:

  • conversations.isolation_env_id → isolation_environments.id (ON DELETE SET NULL): a conversation may be pinned to a git worktree.
  • isolation_environments.created_by_user_id → users.id (ON DELETE SET NULL, migration 041): tracks which user triggered creation of a worktree; nullable since not all creation paths have an attributable user (e.g. webhook-triggered runs).
  • workflow_runs.parent_conversation_id → conversations.id (ON DELETE SET NULL): links a workflow-spawned conversation back to its originating conversation.
  • sessions.parent_session_id → sessions.id (self-reference, no delete action): sessions are immutable — transitions create a new linked row rather than mutating in place.
  • ideas.parent_idea_id → ideas.id (self-reference, no FK constraint declared in SQL, enforced at application level): supports idea hierarchy (epics → features → sub-ideas).
  • workflow_node_sessions has no surrogate id — its primary key is the composite (workflow_name, node_id, scope_key, provider).
  • knowledge_config and knowledge_sources are not scoped to a codebase (global, RAG is install-wide, not per-project).
  • auth_user / auth_session / auth_account / auth_verification are Better Auth’s own tables (web login, opt-in). They are bridged to the canonical users table via user_identities(platform='web', platform_user_id=<auth_user.id>) — not a direct FK.
  • Most ownership FKs cascade (ON DELETE CASCADE); cross-cutting/optional links (user_id, codebase_id on conversations/workflow_runs, isolation_env_id) use ON DELETE SET NULL to avoid destructive cascades on shared/optional references.
