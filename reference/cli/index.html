CLI Reference

Run AI-powered workflows from your terminal.

Quick Start

Section titled “Quick Start”

Note: Workflow and isolation commands require running from within a git repository. Running from subdirectories automatically resolves to the repo root. The version, help, chat, setup, serve, and doctor commands work anywhere.

Commands

Section titled “Commands”

chat <message>

Section titled “chat <message>”

Send a message to the orchestrator for a one-off AI interaction.

setup

Section titled “setup”

Interactive setup wizard for credentials and configuration.

Flags:

FlagEffect
--scope homeWrite to ~/.devox/.env (default). Applies to every project.
--scope projectWrite to <cwd>/.devox/.env. Overrides user scope for this repo only.
--forceOverwrite the target file wholesale instead of merging. A timestamped backup is still written.
--spawnOpen setup wizard in a new terminal window.

Write safety: devox setup never writes to <cwd>/.env — that file belongs to you. The wizard always targets one Devox-owned file chosen by --scope, merges into existing content (so user-added keys survive), and writes a timestamped backup before every rewrite.

doctor

Section titled “doctor”

Verify your Devox setup. Runs a checklist of common failure points: Claude binary spawn, gh CLI auth, Pi auth (when Pi is configured as default), database reachability, workspace writability, bundled defaults, and adapter token pings (Slack/Telegram, best-effort). Also self-heals core agents — deploys any that are missing and warns on stale content.

Exit code 0 if all checks pass or are skipped; 1 if any critical check fails. Adapter pings degrade to skip on network errors — a flaky connection does not flip the result red.

Also runs automatically at the end of devox setup (optional).

agents list

Section titled “agents list”

List all 29 bundled agents with Core/Curated label and deploy status.

Output groups agents into Core (auto-deployed) and Curated (deploy on demand) and shows [deployed] or [not installed] per agent.

agents deploy

Section titled “agents deploy”

Deploy a bundled agent to ~/.claude/agents/ (global, all projects).

devox doctor runs devox agents deploy --core automatically on setup — you only need this to deploy curated agents or to repair a broken core agent.

agents update

Section titled “agents update”

Refresh deployed agents with the latest bundled content.

Unlike deploy, update always overwrites existing files. Use this to pick up improvements shipped in a new Devox release.

agents undeploy

Section titled “agents undeploy”

Remove a deployed agent.

workflow list

Section titled “workflow list”

List workflows available in target directory.

Discovers workflows from .devox/workflows/ (recursive), ~/.devox/workflows/ (global, home-scoped), and bundled defaults. See Global Workflows.

Flags:

FlagEffect
--cwd <path>Target directory (required for most use cases)
--jsonOutput machine-readable JSON instead of formatted text

With --json, outputs { "workflows": [...], "errors": [...] }. Optional fields (provider, model, modelReasoningEffort, webSearchMode) are omitted when not set on a workflow.

workflow run <name> [message]

Section titled “workflow run <name> [message]”

Run a workflow with an optional user message.

Progress events (node start/complete/fail/skip, approval gates) and all structured logs are written to stderr during execution. The final AI response is written to stdout, so they can be separated:

Flags:

FlagEffect
--cwd <path>Target directory (required for most use cases)
--branch <name>Explicit branch name for the worktree
--from <branch>, --from-branch <branch>Override base branch (start-point for worktree)
--no-worktreeOpt out of isolation — run directly in live checkout
--resumeResume from last failed run at the working path (skips completed nodes)
--quiet, -qSuppress all progress and log output (errors only)
--verbose, -vAlso show tool-level events (tool name and duration) and debug-level logs

Default (no flags):

  • Creates worktree with auto-generated branch (devox/task-<workflow>-<timestamp>)
  • Auto-registers codebase if in a git repo

With --branch:

  • Creates/reuses worktree at ~/.devox/workspaces/<owner>/<repo>/worktrees/<branch>/
  • Reuses existing worktree if healthy

With --no-worktree:

  • Runs in target directory directly (no isolation)
  • Mutually exclusive with --branch and --from

Name Matching:

Workflow names are resolved using a 4-tier fallback hierarchy. This applies consistently across the CLI and all chat platforms (Slack, Telegram, Web, GitHub, Discord):

  1. Exact match - devox-assist matches devox-assist
  2. Case-insensitive - Devox-Assist matches devox-assist
  3. Suffix match - assist matches devox-assist (looks for -assist suffix)
  4. Substring match - smart matches devox-smart-pr-review

If multiple workflows match at the same tier, an error lists the candidates:

workflow status

Section titled “workflow status”

Show all running workflow runs across all worktrees.

workflow resume

Section titled “workflow resume”

Resume a failed workflow run. Re-executes the workflow, automatically skipping nodes that completed in the prior run.

workflow abandon

Section titled “workflow abandon”

Discard a workflow run (marks it as cancelled). Use this to unblock a worktree when you don’t want to resume — the path lock is released immediately so a new workflow can start.

workflow approve

Section titled “workflow approve”

Approve a paused workflow run at an interactive approval gate. Optionally provide a comment that is available to the workflow via $LOOP_USER_INPUT.

workflow reject

Section titled “workflow reject”

Reject a paused workflow run at an approval gate. Optionally provide a reason that is available to the workflow via $REJECTION_REASON.

workflow cleanup

Section titled “workflow cleanup”

Delete old terminal workflow run records from the database.

workflow event emit

Section titled “workflow event emit”

Emit a workflow event directly to the database. Primarily used inside workflow loop prompts to record story-level lifecycle events.

Flags:

FlagRequiredDescription
--run-idYesUUID of the workflow run
--typeYesEvent type (e.g., ralph_story_started, node_completed)
--dataNoJSON string attached to the event. Invalid JSON prints a warning and is ignored.

Exit code: 0 on success, 1 when --run-id, --type is missing, or --type is not a valid event type. Event persistence is best-effort (non-throwing) — check server logs if events appear missing.

isolation list

Section titled “isolation list”

Show all active worktree environments.

Groups by codebase, shows branch, workflow type, platform, and days since activity.

isolation cleanup [days]

Section titled “isolation cleanup [days]”

Remove stale environments.

Merge detection uses three signals in order: git branch ancestry (fast-forward / merge commit), patch equivalence (squash-merge via git cherry), and GitHub PR state via the gh CLI. The gh CLI is optional — if absent, only git signals are used.

By default, branches with a CLOSED PR are skipped. Pass --include-closed to clean those up as well. Branches with an OPEN PR are always skipped.

validate workflows [name]

Section titled “validate workflows [name]”

Validate workflow YAML definitions and their referenced resources (command files, MCP configs, skill directories).

Checks: YAML syntax, DAG structure (cycles, dependency refs), command file existence, MCP config files, skill directories, provider compatibility. Returns actionable error messages with “did you mean?” suggestions for typos.

Exit code: 0 = all valid, 1 = errors found.

validate commands [name]

Section titled “validate commands [name]”

Validate command files (.md) in .devox/commands/.

Checks: file exists, non-empty, valid name.

Exit code: 0 = all valid, 1 = errors found.

complete <branch> [branch2 ...]

Section titled “complete <branch> [branch2 ...]”

Remove a branch’s worktree, local branch, and remote branch, and mark its isolation environment as destroyed.

Flags:

FlagEffect
--forceSkip uncommitted-changes guard

Use this after a PR is merged and you no longer need the worktree or branches. Accepts multiple branch names in one call.

Skills follow a two-phase model: first add to the local repository, then deploy to the directories that agents read.

skill add [source]

Section titled “skill add [source]”

Add a skill to the skill repository (~/.devox/skill-repository/). No deployment happens automatically.

Flags:

FlagEffect
--bundledSource is one of the built-in bundled skills
--allAdd all bundled skills (only valid with --bundled)

The Devox skill teaches Claude Code how to work with Devox workflows, commands, and project conventions. It is also added automatically during devox setup.

skill deploy <name>

Section titled “skill deploy <name>”

Copy a skill from the repository into an agent-readable directory.

Flags:

FlagEffect
--globalDeploy to ~/.claude/skills/ (or ~/.agents/skills/ with --universal)
--universalUse .agents/skills/ instead of .claude/skills/
--bundledDeploy directly from bundled binary content (skips repository)
--coreDeploy all 17 core bundled skills globally — shortcut for devox doctor auto-fix

skill undeploy <name>

Section titled “skill undeploy <name>”

Remove a deployed skill from agent directories.

skill update [name …]

Section titled “skill update [name …]”

Re-pull GitHub or bundled skills in the repository. Does not re-deploy.

skill remove <name>

Section titled “skill remove <name>”

Remove a skill from the repository. Does not undeploy it first — undeploy manually if needed.

skill list

Section titled “skill list”

Show skills in the repository or deployment targets.

hooks

Section titled “hooks”

hooks list

Section titled “hooks list”

Show active hooks grouped by event with install status.

--global and --local are mutually exclusive.

hooks install

Section titled “hooks install”

Extract hook scripts to disk and patch provider configs.

What happens:

  1. Scripts extracted to ~/.devox/hooks/ (--global) or <cwd>/.devox/hooks/defaults/
  2. .claude/settings.json (or ~/.claude/settings.json) patched with hook registrations
  3. assistants.copilot.hooks written into ~/.devox/config.yaml (or <cwd>/.devox/config.yaml)

Default behaviour skips scripts that already exist — use --force to overwrite.

hooks disable / enable

command

Section titled “command”

Commands are plain-text Markdown files (.md) used as named AI prompts in workflow command: nodes. Devox ships a set of bundled commands embedded in the binary. The command subcommand lets you list what’s available and extract them to disk for customisation.

command list

Section titled “command list”

Show available commands with source labels.

Flags:

FlagEffect
--globalShow only globally installed commands (~/.devox/commands/)
--localShow only project commands (.devox/commands/)
--jsonOutput JSON: { commands: [{name, description, source}], total, bundled, global, project }

--global and --local are mutually exclusive. Default shows all three sources merged — project overrides global by name, global overrides bundled.

Source labels:

  • bundled — shipped with Devox, available without any install step
  • global — extracted to ~/.devox/commands/ by command install --global
  • project — in .devox/commands/ of the current repo

command install

Section titled “command install”

Extract bundled default commands to disk so you can read, edit, or extend them.

Flags:

FlagEffect
--globalInstall to ~/.devox/commands/ instead of .devox/commands/
--localInstall to .devox/commands/ (explicit, same as default)
--forceOverwrite files that already exist on disk

Default behaviour (no --force): skips any file that already exists. This preserves your customisations. Use --force to reset a command back to the bundled default.

Binary vs source: When running the shipped Devox binary (devox.exe / devox), bundled commands are embedded at compile time — no filesystem access is needed to list or run them. command install extracts these embedded files to disk. In source builds (bun run cli), files are read directly from .devox/commands/defaults/ on disk.

hooks

Section titled “hooks”

Hooks are scripts that run automatically at key points in Claude and Copilot sessions (e.g., before commits, after edits). Devox ships 12 bundled hooks. The hooks subcommand lets you list, extract, and manage them.

hooks list

Section titled “hooks list”

Show all discovered hooks grouped by trigger event.

Flags:

FlagEffect
--globalShow only global hooks (~/.devox/hooks/)
--localShow only project hooks (.devox/hooks/)
--jsonOutput full hook metadata as JSON array

--global and --local are mutually exclusive. Default shows all scopes.

Also shows a warning if hooks have not yet been installed (scripts not yet extracted to disk).

hooks install

Section titled “hooks install”

Extract hook scripts to disk and patch provider configs so hooks activate automatically.

Flags:

FlagEffect
--globalInstall to ~/.devox/hooks/ and patch ~/.devox/config.yaml + ~/.claude/settings.json
--localInstall to .devox/hooks/defaults/ (explicit, same as default)
--forceOverwrite existing .sh scripts on disk
--no-claudeSkip patching .claude/settings.json
--no-copilotSkip patching config.yaml under assistants.copilot.hooks

What happens on install:

  1. Hook scripts (.sh) extracted to ~/.devox/hooks/ (global) or <cwd>/.devox/hooks/defaults/ (local)
  2. .claude/settings.json (or ~/.claude/settings.json) patched with hook registrations — unless --no-claude
  3. assistants.copilot.hooks written to ~/.devox/config.yaml (or <cwd>/.devox/config.yaml) — unless --no-copilot

Default behaviour (no --force): skips scripts that already exist on disk. This preserves any local edits. Use --force to reset scripts to their bundled defaults.

Codex / Pi: hook scripts are extracted to disk but cannot be auto-registered — those providers have no hook API. Call scripts manually from bash: nodes in workflows if needed.

Binary vs source: In the shipped binary, hook scripts are embedded at compile time. hooks install extracts them from the embedded bundle. In source builds, scripts are loaded from .devox/hooks/defaults/ on the filesystem.

hooks disable / enable

Section titled “hooks disable / enable”

Exclude or re-include a hook via .devox/config.yaml:

Writes the hook name into globalHooks.exclude in the appropriate config file. Does not delete the script from disk — the script remains available for manual use or future re-enabling.

rules

Section titled “rules”

Rules are Markdown documents that Devox injects into the AI system prompt of every conversation and workflow node — for all providers (Claude, Copilot, Codex, Pi). Devox ships 3 bundled rules (always, code-quality, security). The rules subcommand lets you list and manage them.

No installation step is needed. Rules are discovered at conversation time and injected automatically.

rules list

Section titled “rules list”

Show all active rules from all scopes.

Flags:

FlagEffect
--globalShow only global rules (~/.devox/rules/)
--localShow only project rules (.devox/rules/)
--jsonOutput rule names and sources as a JSON array

--global and --local are mutually exclusive. Default shows all scopes.

Example output:

rules disable / enable

Section titled “rules disable / enable”

Exclude or re-include a rule via .devox/config.yaml:

Writes the rule name into globalRules.exclude in the appropriate config file.

Note: disable / enable only affects bundled rules. User-global (~/.devox/rules/) and project (.devox/rules/) rules always load — remove the file from disk to stop them loading.

Adding custom rules — no CLI needed, just create a file:

See the Global Rules guide for the full reference including scope precedence, override behaviour, and rule-writing tips.

mcp

Section titled “mcp”

MCP (Model Context Protocol) configs are JSON files that define external tool servers (e.g., GitHub, Linear, Jira). Devox ships bundled configs for common services. The mcp subcommand lets you list and extract them.

mcp list

Section titled “mcp list”

Show available MCP server configs with package reference and required env vars.

Flags:

FlagEffect
--globalShow only globally installed configs (~/.devox/mcp/)
--localShow only project configs (.devox/mcp/)
--jsonOutput JSON array with name, command, args, envVars fields

--global and --local are mutually exclusive. Default shows all bundled configs with install instructions.

The all view lists every bundled config with the npm package it wraps and the env vars it requires — useful for knowing what to set before using a config in a workflow.

mcp install

Section titled “mcp install”

Extract bundled MCP configs to disk.

Flags:

FlagEffect
--globalInstall to ~/.devox/mcp/ instead of .devox/mcp/
--localInstall to .devox/mcp/ (explicit, same as default)
--forceOverwrite configs that already exist on disk
--dry-runPrint what would be installed; write nothing

Default behaviour (no --force): skips any config file that already exists on disk (“disk wins”). This preserves any env-var edits or customisations you’ve made to a config. Use --force to reset a config back to the bundled default.

Using configs in workflows — the path you write in mcp: determines which file is used:

ReferenceResolves toPicks up
mcp: github.json<cwd>/github.json → falls back to ~/.devox/mcp/github.jsonGlobal install or bundled auto-extract
mcp: .devox/mcp/github.json<cwd>/.devox/mcp/github.json → falls back to ~/.devox/mcp/github.jsonProject-local install, then global/bundled

Important: bare name (github.json) resolves relative to cwd, not inside .devox/mcp/. If you ran mcp install --local and want to use that project copy, you must reference it with the full relative path shown above.

Devox auto-extracts the bundled copy to ~/.devox/mcp/ on first use — you don’t need to run mcp install at all to use the defaults.

Supported providers: Claude ✅ Copilot ✅ Codex ❌ Pi ❌

Binary vs source: In the shipped binary, MCP configs are embedded at compile time. mcp install extracts them from the embedded bundle. In source builds, configs are read from .devox/mcp/defaults/ on the filesystem. Either way, once extracted to disk the file is used as-is — the binary copy is only a fallback.

serve

Section titled “serve”

Start the web UI server. On first run, downloads a pre-built web UI tarball from the matching GitHub release, verifies the SHA-256 checksum, and extracts it. Subsequent runs use the cached copy.

Binary installs only — in development, use bun run dev instead.

Flags:

FlagEffect
--port <port>Override server port (default: 3090, range: 1–65535)
--download-onlyDownload and cache the web UI, then exit without starting the server

The cached web UI is stored at ~/.devox/web-dist/<version>/. Each version is cached independently, so upgrading the binary automatically downloads the matching web UI.

Global Options

Section titled “Global Options”
OptionEffect
--cwd <path>Override working directory (default: current directory)
--globalInstall/list globally (~/.devox/…, applies to all projects)
--localInstall/list locally (<cwd>/.devox/…, current project only)

Working Directory

Section titled “Working Directory”

The CLI determines where to run based on:

  1. --cwd flag (if provided)
  2. Current directory (default)

Running from a subdirectory (e.g., /repo/packages/cli) automatically resolves to the git repository root (e.g., /repo).

When using --branch, workflows run inside the worktree directory.

Commands and workflows are loaded from the working directory at runtime. The CLI reads directly from disk, so it picks up uncommitted changes immediately. This is different from the server (Telegram/Slack/GitHub), which reads from the workspace clone at ~/.devox/workspaces/ — that clone only syncs from the remote before worktree creation, so changes must be pushed to take effect there.

Environment

Section titled “Environment”

At startup, the CLI strips all Bun-auto-loaded CWD .env keys and nested Claude Code session markers from process.env, then loads two Devox-owned env files with override: true. Keys in Devox-owned files pass through to AI subprocesses — no allowlist filtering.

On startup, the CLI:

  1. Strips <cwd>/.env* keys + CLAUDECODE markers from process.env (via stripCwdEnv). Emits [devox] stripped N keys from <cwd> (...) when N > 0.
  2. Loads ~/.devox/.env (user scope). Emits [devox] loaded N keys … when N > 0.
  3. Loads <cwd>/.devox/.env (project scope, overrides user scope). Emits [devox] loaded N keys … (repo scope, overrides user scope) when N > 0.
  4. Auto-enables global Claude auth if no explicit tokens are set.

<cwd>/.env is never loaded — it belongs to the target project. See Configuration Reference: .env File Locations for the full three-path model.

Database

Section titled “Database”
  • Without DATABASE_URL (default): Uses SQLite at ~/.devox/devox.db — zero setup, auto-initialized on first run
  • With DATABASE_URL: Uses PostgreSQL (optional, for cloud/advanced deployments)

Both work transparently. Most users never need to configure a database.
