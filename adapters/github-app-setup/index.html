GitHub App Setup

This is the recommended GitHub auth mode for teams sharing one Devox instance. It replaces the shared GITHUB_TOKEN PAT with a registered GitHub App so that:

  • Bot comments appear as devox[bot] with the App badge, not under an operator’s personal account.
  • Installation access tokens rotate automatically every ~1 h (smaller blast radius if leaked).
  • Webhooks centralise — one URL per App covers every installation.
  • Repos can span multiple GitHub orgs (or a mix of orgs and personal accounts) — Devox routes per-(owner, repo) to the right installation automatically.

Solo installs that only need the PAT model can ignore this page; see GitHub for the legacy setup.

SituationRecommended mode
Solo developer, single GitHub accountPAT
Team of 2+ sharing one Devox instanceApp
Repos across multiple orgsApp
You want bot comments attributed as <slug>[bot] with App badgeApp
You want short-lived (1 h) tokens instead of a long-lived PATApp

Mutual exclusion

Devox refuses to start with both modes configured. Pick one set of env vars — either GITHUB_TOKEN (PAT) or GITHUB_APP_ID (App), never both.

Step 1: Register the GitHub App

Section titled “Step 1: Register the GitHub App”

  1. Go to https://github.com/settings/apps/new (or https://github.com/organizations/<org>/settings/apps/new for an org-owned App).

  2. Fill in:

    • GitHub App name — e.g. Devox Bot. The slug derived from this (visible in the App URL) is what you’ll later set as GITHUB_APP_SLUG. The bot’s posted-comment login is <slug>[bot].
    • Homepage URL — your team’s Devox URL, e.g. https://devox.example.com/.
    • Webhook URL — https://devox.example.com/webhooks/github.
    • Webhook secret — same value as your WEBHOOK_SECRET env var.

  3. Uncheck Active on the user authorisation callback URL — Devox doesn’t use GitHub OAuth in this flow (the device-flow for per-user attribution is separate).

Step 2: Set Repository Permissions

Section titled “Step 2: Set Repository Permissions”

Under Repository permissions, set:

PermissionAccessUsed for
ContentsReadCloning + reading repo metadata
IssuesRead & WritecreateComment + listComments
Pull requestsRead & Writepulls.get + comment posting
MetadataReadMandatory (auto-included by GitHub)

Account permissions: none.

Under Subscribe to events, select:

  • Issue comments
  • Pull request review comments
  • Pull request
  • Issues (used for closed cleanup)

Step 3: Generate a Private Key

Section titled “Step 3: Generate a Private Key”
  1. After saving the App, scroll to Private keys and click Generate a private key.
  2. Save the downloaded .pem file somewhere only readable by the Devox process — e.g. /etc/devox/github-app.pem.

Step 4: Install the App on Your Orgs

Section titled “Step 4: Install the App on Your Orgs”

Install the App on every org or personal account that holds repos your team operates on:

  1. From the App settings page, click Install App.
  2. Pick the org → grant access to All repositories (or selected repos).
  3. Repeat for every org/account.

Multi-installation routing

Devox resolves owner/repo → installation_id automatically via GET /repos/{owner}/{repo}/installation. No per-install config is needed unless you have exactly one installation — see GITHUB_APP_INSTALLATION_ID in Step 5.

Step 6: Verify the Setup

Section titled “Step 6: Verify the Setup”
  1. Remove GITHUB_TOKEN from your env (Devox refuses to start if both are set).
  2. Restart the server.
  3. Confirm the startup log shows github.adapter_mode_app with your slug.
  4. Trigger a webhook from a repo where the App is installed (e.g. comment @devox ping on an issue).
  5. Confirm the bot’s reply appears as <slug>[bot] with the App badge in the GitHub UI.

How Token Caching Works

Section titled “How Token Caching Works”

Installation tokens are valid for 1 h. Devox caches each installation_id → token pair and refreshes ~5 minutes before expiry on next access. No background timer — no leaked handles; the process survives suspend/resume cleanly.

Every webhook delivery from a GitHub App carries installation.id. Devox primes its owner/repo → installation_id cache from the payload, so the next outbound call to that repo skips the GET /repos/{owner}/{repo}/installation round trip.

A 401 from any installation Octokit evicts the cached token and the call is retried once with a fresh token. Persistent 401s propagate as the original error.

Workflows Longer Than 1 Hour

Section titled “Workflows Longer Than 1 Hour”

Workflows that span >1 h need a fresh token to push from the cloned worktree. Devox installs a git credential helper at clone time (App mode only): the worktree’s .git/config points at scripts/git-credential-devox.sh, which calls back to Devox’s internal endpoint (POST /internal/git-credential) for a live installation token on each git operation.

Compiled binary builds

The credential helper is installed from scripts/git-credential-devox.sh in the source tree. Compiled binaries that don’t ship scripts/ on disk silently skip the install — workflows up to 1 h still succeed via the URL-embedded installation token, but longer workflows will see git push fail with “Authentication failed” past the 1 h mark.

Security: Protecting the Internal Endpoint

Section titled “Security: Protecting the Internal Endpoint”

The credential-helper backend at POST /internal/git-credential hands out live installation access tokens. It must NOT be reachable from outside the Devox host.

Devox enforces this at startup: with App mode active and the server bound to a non-loopback interface (e.g. 0.0.0.0), the process refuses to start and exits with github_app.internal_endpoint_public_bind_rejected.

Two correct configurations:

  1. Recommended — bind Devox to 127.0.0.1 (HOST=127.0.0.1) and put a reverse proxy in front. Configure the proxy to drop /internal/* paths.

  2. Opt-in escape hatch — DEVOX_ALLOW_INTERNAL_ON_PUBLIC_BIND=1 combined with HOST=0.0.0.0 (or unset). Use only when your reverse proxy already drops /internal/* AND your deployment topology genuinely requires a non-loopback bind (e.g. a container network where loopback isn’t reachable from the proxy). Startup logs github_app.internal_endpoint_exposed_acknowledged so the choice is auditable.

Migrating from PAT Mode

Section titled “Migrating from PAT Mode”
  1. Register the App and install on your orgs (Steps 1–4 above).
  2. Add GITHUB_APP_* env vars (Step 5).
  3. Remove GITHUB_TOKEN from your env (or comment it out). Devox refuses to start if both are set.
  4. Restart Devox.
  5. Existing per-repo webhooks configured for PAT mode can stay or be removed — the App’s single webhook URL covers everything once it’s installed. New repos auto-join via App installation.

Troubleshooting

Section titled “Troubleshooting”

Private key issues

Section titled “Private key issues”
  • Check the file content includes -----BEGIN ... PRIVATE KEY----- and -----END ... PRIVATE KEY-----.
  • For inline keys, ensure the .env value preserves newlines — either literal newlines in a multi-line value, or the \n escape inside double quotes.

404: App not installed on this owner

Section titled “404: App not installed on this owner”

The App is not installed on that owner’s org/account. Click Install App on the App settings page and grant access to the target org/account.

Repeated 401s on outbound API calls

Section titled “Repeated 401s on outbound API calls”

createComment, listComments, repos.get, pulls.get returning 401 points to installation/token issues — not webhook config:

  • Verify the App is installed on the target owner and has not been suspended or uninstalled (https://github.com/settings/installations).
  • Verify the App’s permissions still include the required scopes (Contents:Read for clone; Issues:RW + Pull requests:RW for comments). Permission scope changes require each installation operator to review and accept the new permissions — Devox will 401 until that’s done.
  • Verify the private key in your env (GITHUB_APP_PRIVATE_KEY or _PATH) matches the same App that GITHUB_APP_ID points at. Mismatched key + ID causes “401 from JWT” at token-issuance time.
  • Verify GITHUB_APP_INSTALLATION_ID (if set) still corresponds to a live installation — uninstall + reinstall assigns a new ID.

Webhook secret mismatch

Section titled “Webhook secret mismatch”

A webhook-secret mismatch causes github.signature_mismatch / github.signature_length_mismatch at the POST /webhooks/github endpoint. If GitHub’s webhook delivery page shows red ❌, check that WEBHOOK_SECRET in Devox’s env matches the value entered in the GitHub App’s webhook configuration page exactly.

Server refuses to start: still in PAT mode

Section titled “Server refuses to start: still in PAT mode”

Check process.env.GITHUB_TOKEN is unset and GITHUB_APP_ID is set; restart.

Server refuses to start: public bind with App mode

Section titled “Server refuses to start: public bind with App mode”

App mode is active but the server is bound to a non-loopback interface. Either set HOST=127.0.0.1 (recommended), or — if your reverse proxy already drops /internal/* and you genuinely need a non-loopback bind — set DEVOX_ALLOW_INTERNAL_ON_PUBLIC_BIND=1.
